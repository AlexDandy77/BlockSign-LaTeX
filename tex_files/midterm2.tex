\section{Back-end architecture}
The back-end of the system has been developed with a focus on scalability, modularity, and security. Its purpose is to provide all the critical functionality required for user registration, authentication, document management, and secure verification of signatures (Figure \ref{main-project-routers}). 

\begin{figure}[H]
    \centering
    \includegraphics[width=18cm]{"images/main-project-routers.png"}
    \caption{Main Project Routers}
    \label{main-project-routers}
\end{figure}

The implementation relies on Node.js with the Express.js framework, while data persistence is handled by PostgreSQL through the Prisma ORM.

\subsection{Application Layer}
The server is structured around separate route modules, each of which is responsible for a specific part of the functionality. For example, the auth.routes.ts file manages the passwordless login process using challenge–response verification, while registration.routes.ts covers the steps of email OTP verification, registration requests, and account completion with a public key. The administrator’s responsibilities, such as reviewing and approving registration requests, are implemented in admin.registration.routes.ts. Finally, user-oriented functionality, including profile management and document operations, is centralized in user.routes.ts. This modular design improves maintainability and makes it easier to extend the system in the future.

\subsection{Database Layer}
The database schema is implemented using Prisma ORM on top of PostgreSQL. Entities such as User, RegistrationRequest, Document, DocumentParticipant and Signature are modeled explicitly with foreign keys and unique constraints to guarantee consistency (Figure \ref{user-db-model}). 

\begin{figure}[H]
    \centering
    \includegraphics[width=18cm]{"images/user-db-model.png"}
    \caption{User Database Model}
    \label{user-db-model}
\end{figure}

The use of Prisma Client enables type-safe queries and simplifies operations like migrations, seeding, and testing.

\subsection{Security Measures}
The architecture incorporates several security mechanisms. Authentication challenges are valid only for five minutes and become invalid once used. Refresh tokens are stored in secure cookies to reduce exposure. The use of Ed25519 ensures modern cryptographic security, while SHA-256 guarantees the integrity of documents. Finally, file validation ensures that only PDF documents are accepted.

\subsection{Authentication and Tokens}
Authentication in the system is fully passwordless and relies on public/private key pairs. Users prove their identity by signing challenges provided by the server. Successful verification grants them access tokens and refresh tokens in the form of JWTs.

Access tokens are short-lived and returned in the response body, while refresh tokens are long-lived and stored securely in HTTP-only cookies. Middleware functions such as requireUser and requireAdmin check the validity of tokens and enforce role-based access control.

\subsection{Email Service}
The system integrates Nodemailer as an email delivery mechanism configured with SMTP credentials for the project’s domain. Emails are used in two important contexts. First, during registration, users receive a six-digit OTP code for email validation. Second, during document workflows, participants receive notifications when they are asked to review and sign a document, and again when the document has been finalized (Figure \ref{email-sending}).

\subsection{Cryptographic Module}
Security of authentication and documents is achieved with the Ed25519 digital signature scheme, implemented via the @noble/ed25519 library (Figure \ref{keygen}). 

\begin{figure}[H]
    \centering
    \includegraphics[width=18cm]{"images/keygen.png"}

A dedicated crypto utility handles key pair generation, signing, and verification of messages. In addition, SHA-256 is used for hashing documents, ensuring their integrity before they are accepted or signed.

\subsection{Document Workflow}
The MVP implementation of the document signing process follows a well-defined lifecycle. When a user creates a document, they upload the file, calculate its SHA-256 hash, and sign a canonical payload. The payload and initial signature are stored in the database.

Participants selected by the creator receive an email with the PDF attached and the corresponding hash. Each participant is expected to calculate the hash independently, compare it with the payload, and if it matches, sign the document (Figure \ref{payload-signature}). 

\begin{figure}[H]
    \centering
    \includegraphics[width=18cm]{"images/payload-signature.png"}
    \caption{Build Paylaod and Verify Signature}
    \label{payload-signature}
\end{figure}

Their signatures are then added to the database. Once all required signatures are collected, the document status changes to signed, and a notification is sent to all involved parties.

\subsection{Extensibility}
The modular design of the back-end makes it adaptable to future improvements. Currently, the project works on Polygon blockchain, but there can be added the functionality of choosing the blockchain network by the document creator. Similarly, while usernames are currently used to tag participants, the design leaves room for later integration with decentralized identity systems or phone book integrations.

\section{iOS Mobile Application}
The BlockSign iOS application extends the platform's capabilities to mobile devices, providing users with a native, secure, and user-friendly experience for managing digital signatures on the go. Built using SwiftUI and following Apple's Human Interface Guidelines, the application maintains feature parity with the web platform while leveraging iOS-specific capabilities for enhanced security and usability.

\subsection{Mobile Architecture}
The iOS application follows the MVVM (Model-View-ViewModel) architectural pattern, ensuring clear separation of concerns and maintainable code structure. The architecture is designed to handle offline scenarios gracefully while maintaining cryptographic security standards.

\subsubsection{Core Components}
The application is structured around several key architectural components that work together to provide a seamless user experience. The Models layer defines data structures representing users, documents, signatures, and registration workflows, ensuring type-safe data handling throughout the application. ViewModels serve as the business logic layer, managing authentication flows, document operations, and registration processes while maintaining clean separation from the presentation layer. The Views layer consists of SwiftUI-based user interface components that provide intuitive navigation and interaction patterns optimized for mobile devices. Services provide utility modules for critical functions including API communication, biometric authentication, and cryptographic operations. Finally, the Utils layer includes helper functions for BIP-39 mnemonic generation, application theming, and configuration management, supporting the core functionality with reusable utilities.

\subsection{Authentication and Security}
The mobile application implements passwordless authentication using Ed25519 digital signatures, maintaining consistency with the web platform's security model. Users authenticate by signing cryptographic challenges with their private keys, which are securely derived from BIP-39 mnemonic phrases.

\subsubsection{Biometric Integration}
The iOS application leverages native biometric authentication capabilities to provide seamless and secure access. Face ID serves as the primary biometric authentication method on supported devices, offering quick and secure access without requiring manual credential entry. For devices without Face ID (Figure \ref{mobile-login}), Touch ID provides an alternative biometric option, ensuring all users can benefit from biometric security. Mnemonic phrases and private keys are stored securely using iOS Keychain Services, which provides hardware-backed encryption on devices with Secure Enclave. The application integrates deeply with the LocalAuthentication framework to handle biometric verification, including fallback scenarios and user cancellation gracefully.

\subsubsection{Cryptographic Implementation}
The application implements client-side cryptography using native Swift libraries and carefully selected third-party packages to ensure maximum security and compatibility. The BIP-39 implementation handles mnemonic phrase generation and validation following Bitcoin Improvement Proposal 39 standards, ensuring compatibility with industry-standard wallet recovery mechanisms. For key derivation, the application uses SLIP-0010 to generate hierarchical deterministic Ed25519 keys from the mnemonic phrase, allowing for secure and reproducible key generation. Ed25519 signature generation and verification are implemented using a pure Swift implementation, eliminating external dependencies for this critical security function. Document integrity verification relies on SHA-256 hashing implemented through the CommonCrypto framework, providing fast and reliable hash computation. When users opt for additional security with PIN codes, the application employs PBKDF2 for key derivation, adding an extra layer of protection. All cryptographic operations are performed locally on the device, ensuring that private keys never leave the user's control.

\section{DevOps \& Deployment}
The BlockSign platform implements a robust DevOps pipeline that ensures reliable deployments, continuous integration, and production environment stability. The infrastructure is designed for scalability, security, and maintainability, leveraging Amazon Web Services (AWS) for cloud infrastructure and Xcode Cloud for mobile application deployment.

\subsection{Cloud Infrastructure}
The production environment is hosted on AWS, utilizing multiple services to create a secure, scalable, and reliable infrastructure. Amazon EC2 (Elastic Compute Cloud) instances provide the computing resources for hosting the back-end application, offering flexible instance types that can be scaled vertically or horizontally based on demand. An Elastic IP address ensures the production server maintains a consistent public IP address even when instances are replaced or restarted, simplifying DNS configuration and maintaining stable endpoint addresses for client applications.

Document storage is handled through Amazon S3 (Simple Storage Service), which provides highly durable and scalable object storage for uploaded PDF files. S3's built-in redundancy and versioning capabilities ensure document availability and enable recovery from accidental deletions. Email delivery relies on Amazon SES (Simple Email Service) for sending OTP codes, registration notifications, and document signing invitations, providing reliable email delivery with high deliverability rates and detailed sending metrics.

AWS IAM (Identity and Access Management) controls access to AWS resources, implementing the principle of least privilege by granting services and users only the permissions they require. IAM roles enable EC2 instances to securely access S3 buckets and SES without storing long-term credentials, while IAM policies define granular permissions for different components of the infrastructure.

\subsection{Mobile Application Deployment}
The iOS application utilizes Xcode Cloud for automated building and deployment, integrating seamlessly with the GitHub repository. Xcode Cloud automatically builds the application whenever changes are pushed to the main branch, running unit tests and generating signed builds for TestFlight distribution. This automated workflow eliminates manual build processes and ensures consistent build environments, reducing the potential for environment-specific build issues. TestFlight enables beta testing with both internal and external testers before production release, providing valuable feedback and identifying issues before they reach the App Store.

\subsection{Containerization Strategy}
The back-end application is fully containerized using Docker, enabling consistent deployment across development, staging, and production environments.

\subsubsection{Docker Configuration}
The Docker setup includes optimized multi-stage builds that significantly reduce image sizes while improving security posture. The base image uses Node.js on Alpine Linux, providing a minimal footprint that includes only essential system libraries and reducing the attack surface. The build stage handles compilation of TypeScript source code to JavaScript, installing only production dependencies and excluding development tools from the final image. The production stage creates a minimal runtime image containing only necessary files for application execution, further reducing image size and potential vulnerabilities. Strategic layer ordering enables efficient rebuilds by placing frequently changing code layers after stable dependency layers, improving build cache utilization. Automated vulnerability scanning of container images runs during the build process, identifying and flagging security issues in both base images and application dependencies before deployment.

\subsubsection{Docker Compose Orchestration}
The application uses Docker Compose for orchestrating multiple services in both local development and production deployment scenarios. Service definitions specify the Node.js application container along with the PostgreSQL database and an optional Redis cache for session management and API response caching. Network configuration creates isolated internal networks that enable secure service-to-service communication while restricting external access to only necessary entry points. Volume management provides persistent storage for database data, while uploaded documents are stored in Amazon S3 rather than local volumes, providing scalable and durable storage with built-in redundancy. Environment variables are securely injected through environment files that remain outside version control, protecting sensitive configuration data including AWS credentials while allowing easy environment-specific customization. Health checks monitor container status and automatically restart failed services, improving system reliability and reducing manual intervention requirements.

\subsection{Database Management}
Database operations are managed through Prisma ORM with comprehensive migration support:

\subsubsection{Migration Strategy}
Database operations follow a comprehensive migration strategy that ensures data integrity throughout the application lifecycle. Schema versioning through Git-tracked migration files creates reproducible database states that can be reliably deployed across multiple environments. Automated migrations execute as part of the deployment pipeline, applying pending schema changes before starting updated application code. Pre-migration database backups provide safety nets, allowing quick recovery if migration issues cause data corruption or unexpected schema changes. Rollback support enables reverting problematic migrations, though this capability is used cautiously due to the complexity of reversing data transformations. Seeding functionality populates initial data for development and testing environments, ensuring consistent baseline data for quality assurance and local development work.

\subsubsection{Database Security}
Database security implements multiple layers of protection to safeguard sensitive user and document data. Connection security mandates TLS/SSL encryption for all database connections, preventing man-in-the-middle attacks and ensuring data confidentiality during transmission. Access control uses role-based database user permissions, limiting each application component to only the database operations it requires and reducing the potential impact of security breaches. Credential management relies on environment variable-based injection rather than hardcoded values, keeping database passwords out of source code and configuration files committed to version control. Automated backup scheduling runs regular database backups with configurable retention policies, balancing storage costs against data recovery requirements. Performance monitoring tracks query execution times and identifies slow queries, enabling optimization of database access patterns and preventing performance degradation as data volumes grow.

\subsection{Environment Configuration}
The application supports multiple deployment environments with distinct configurations tailored to each use case. Development environments provide local development capabilities with hot-reloading that automatically refreshes the application when code changes, along with verbose debug logging that aids troubleshooting. Staging environments mirror production configuration as closely as possible, providing a pre-production testing ground where new features can be validated under production-like conditions before general release. Production environments use optimized settings including minified assets, reduced logging verbosity, and enhanced security measures to maximize performance and protect sensitive data. \subsection{Monitoring and Logging}
Production deployments include comprehensive monitoring and logging infrastructure that provides visibility into application health and performance. Application monitoring utilizes dedicated health endpoints that respond to HTTP requests, enabling both automated monitoring systems and manual health checks to verify service availability. Performance metrics track response times for API endpoints, identifying slow operations and enabling proactive optimization before users experience degraded performance. Error tracking automatically captures and reports application exceptions, providing detailed stack traces and context information that accelerate debugging and resolution. Resource monitoring tracks CPU utilization, memory consumption, and disk usage patterns, alerting operations teams before resource exhaustion causes service disruption. External uptime monitoring services poll the application from multiple geographic locations, detecting regional outages and verifying global availability.

The logging strategy implements structured logging throughout the application, with JSON-formatted log entries that enable efficient machine parsing and analysis. Appropriate log levels distinguish between debug information useful during development, informational messages about normal operations, warnings about potential issues, and errors requiring immediate attention. Centralized log aggregation collects logs from all application instances into a unified system, simplifying troubleshooting across distributed deployments and enabling correlation of events across multiple services. Time-based log rotation and archival balance the need for historical data against storage costs, retaining recent logs for quick access while archiving older logs to cheaper storage tiers. Security logging creates comprehensive audit trails for authentication attempts, authorization decisions, and sensitive operations, supporting both security investigations and compliance requirements.

\subsection{Security Hardening}
Production deployments implement multiple layers of security hardening to protect against common attack vectors. HTTPS enforcement through SSL/TLS certificates with automatic renewal ensures all client-server communication remains encrypted, with modern cipher suites that balance security and performance. Firewall configuration restricts port access to only necessary services while implementing IP whitelisting for administrative interfaces, reducing the attack surface available to potential attackers. Rate limiting applies request throttling to prevent abuse, protecting against denial-of-service attacks and automated credential stuffing attempts while allowing legitimate high-volume users to operate normally. Security headers including Content Security Policy, HTTP Strict Transport Security, and X-Frame-Options protect against cross-site scripting, protocol downgrade attacks, and clickjacking vulnerabilities. Automated dependency scanning continuously monitors npm packages for known vulnerabilities, alerting when security updates become available and enabling proactive patching before exploits emerge. Container security measures include running processes as non-root users and applying minimal file system permissions, limiting the potential damage from container escape vulnerabilities.

\subsection{Scalability Considerations}
The infrastructure is designed from the ground up to support horizontal scaling as user demand grows over time. The stateless application design ensures servers maintain no local state, storing all session data in shared storage systems like Redis, which enables adding or removing application instances without affecting user sessions or requiring complex synchronization. Load balancing distributes incoming traffic across multiple application instances, improving both performance and reliability by preventing any single server from becoming a bottleneck. Database scaling support includes provisions for read replicas that handle query operations while the primary database handles writes, along with connection pooling that efficiently manages database connections across multiple application instances. Caching strategy implementation through Redis integration stores frequently accessed data in memory, dramatically reducing database load and improving response times for common queries. CDN integration distributes static assets like images, stylesheets, and JavaScript files through geographically distributed content delivery networks, reducing latency for users worldwide. The modular architecture remains microservices-ready, with clear boundaries between components that facilitate future decomposition into separate services if scaling requirements demand more granular deployment control.

\subsection{Disaster Recovery}
Comprehensive disaster recovery procedures ensure business continuity even in the face of catastrophic failures. The backup strategy implements automated daily backups of both database content and critical configuration files, with Amazon S3 providing durable storage for backup archives with configurable retention periods that balance recovery capabilities against storage costs. Regular backup verification through periodic restoration tests ensures backup integrity and validates that recovery procedures work as documented, preventing unpleasant surprises during actual disaster scenarios. S3's built-in geo-redundant storage replicates backups across multiple AWS availability zones, protecting against regional disasters like data center failures or natural disasters that could destroy primary infrastructure. Documented Recovery Time Objectives establish target timeframes for restoring service after various failure scenarios, guiding infrastructure investments and operational procedures. Recovery Point Objectives define maximum acceptable data loss thresholds, informing backup frequency and transaction log retention policies. A detailed incident response plan documents step-by-step procedures for handling different types of outages, ensuring operations teams can execute recovery efficiently even under stress, with clear escalation paths and communication protocols. The use of Elastic IP addresses simplifies recovery by allowing quick reassignment to replacement EC2 instances without requiring DNS propagation delays.
